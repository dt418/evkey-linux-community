01 · runtime / module

Runtime path and helper boundary

Open runtime diagram directlyFrame loads lazily; this link opens standalone document.

Text equivalent

  • An application supplies an input context to Fcitx5; the EVKey add-on uses Bamboo/Lotus integration to transform composition, then Fcitx commits composed text back to the application.
  • Settings communicates with Fcitx Controller through the session D-Bus. This is distinct from AF_UNIX between the add-on and helper.
  • For Smooth/Uinput, the add-on sends only bounded editing-key requests to the optional helper; the helper receives neither composed text nor raw keyboard input.
  • Before output through /dev/uinput, the helper checks peer UID plus active, local, unlocked desktop-session state. Those checks permit a request; they do not guarantee the application applied an edit.

02 · input mode / fallback

Requested, effective, and fallback modes

Open input-mode diagram directlyFrame loads lazily; this link opens standalone document.

Text equivalent

  • Requested mode is the saved global or application rule. Effective mode is selected for the focused input context and can differ from that saved choice.
  • Preedit keeps composition separate from application text until commit. Fake Backspace replaces an engine-owned suffix with application-directed Backspace events, then commits through Fcitx.
  • Smooth/Uinput is available only when both input-context conditions and the optional helper permit it. If the helper rejects a request or is unavailable, the engine may fall back to Preedit.
  • Fallback does not claim universal application compatibility. An interrupted replacement is not described as blindly retried or universally safe.
